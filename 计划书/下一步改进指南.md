## 2. 根因分析（为什么会有这些问题）

### 2.1 资源依赖与「诚实化」之间的张力

`include_bytes!("../../libs/large.onnx")` 让模型成为**编译期硬依赖**（`server/src/yolo.rs:24`）。占位文件能解锁编译，但会给出「识别已实现」的假象；真实运行时没有有效模型 = 识别必然失败。这是当前「测试全绿但产品不可用」的结构性根因之一。

### 2.2 Rust 侧 unwrap 成灾

`listen.rs` 的 `xcap::Window::all().unwrap()`、`window.capture_image().unwrap()`，`worker.rs` 的 `predict(image).unwrap()`、`app.emit(...).unwrap()`，`engine/mod.rs` 的 `child.stdin.take().unwrap()` 等，把「窗口被关、截屏失败、引擎异常退出、模型未加载」全部变成后台线程 panic。`start_listen` 中 `predict(image).unwrap()` 一旦失败，监听线程直接崩溃且 UI 仍可能显示「运行中」。这正是 SELF-REVIEW §3 指出的「只修表面没打通链路」的延续。

### 2.3 前端布局是「为 1080p 单窗口写死」

`App.vue` 用 `position: absolute` + 固定像素（`left:400px`、`width:630px` 等）；`Analyse.vue` 的 `.textlog` 固定 `260×440` 并 `left:400px`；`Chessboard.vue` 硬编码 `a0…i9` 90 个格子。这套设计只适配单一分辨率，无 `flex/grid`、无响应式断点、无键盘/焦点管理、无触控目标尺寸，移动/小窗/高分屏缩放都会错位。

### 2.4 配置「改了不生效 / 无反馈」

前端抽屉每次 `@update:value` 直接 `invoke` 写库，但：

- 引擎在监听线程内已被锁快照克隆，运行中改 depth/time/threads/hash 不会影响当前搜索；
- `reload_engine` 命令存在但**前端从未调用**（CONTRACT.md §5 明确「保留命令」）；
- 保存没有成功/失败 toast，也没有「失败还原」。
  用户以为改了配置，实际可能要重启才生效——这是典型的「伪反馈」。

### 2.5 测试覆盖「重契约、轻真实路径」

14 个单测 + 1 条 E2E 主要验证渲染与契约集合，没有「选窗口 → 启动 → 识别失败 → 错误恢复 → 停止」的真实用户路径，也没有对 Rust 错误路径（Engine EOF、窗口关闭、模型缺失）的回归。覆盖率阈值 50/40/40/50 偏低，距离用户要求的「100%」很远（对桌面原生部分需要务实目标，见 §6.6）。

## 3. 改进目标（SMART）

1. **可验证性**：拿到真实 `large.onnx`（或改为动态加载）后，`cargo check/clippy/test` 与 `pnpm` 全门禁在干净环境一条命令跑绿，并给出真实棋盘识别 E2E 证据。
2. **可靠性**：Rust 侧**零非预期 panic**（所有命令/线程路径 Result 化 + 前端错误反馈），监听线程状态可观测、可停止、可恢复。
3. **体验**：任意分辨率/窗口尺寸不错位；键盘可操作；配置保存有反馈且**热生效**；新手 3 分钟能跑通「选窗→启动→看懂结果」。
4. **产品扩展**：图片识别、复制局面、局面导出、对局复盘、人机/连线对战按里程碑落地（含 TDD 与验收矩阵）。
5. **工程卫生**：清理占位/裁剪模型与旧产物，补齐文档索引/ADR/资源门禁单轨，提交前全量验证并保护工作区改动。

## 8. 回滚与保护

- **保护**：`libs/pikafish/*` 工作区改动（官方引擎替换）绝不 reset/restore/clean；`git add .` 禁用；按主题 `git add <files>` 精确提交。
- **回滚**：每阶段改动先提交或记录 diff 快照；失败时 `git checkout -- <文件>`（仅限本次改动，禁止全局）；配置变更由后端原子写 + `.bak` 兜底；发布回滚见 docs/SOP.md §5。
- **清理**：删除任何文件（`.bak-orig`、旧产物、死代码）前，先确认其在 `git status` 中的角色（跟踪/未跟踪）并留档，不做大范围强制清理。
